## 一、项目概述

### 1.1 一句话

输入一句故事创意，输出**一本绘本 PDF、一段 5 分钟有声书、一条带字幕的短视频**，
且角色在三种模态里是同一个人。

### 1.2 覆盖的模态

| 模态 | 产物 | 规模 |
| --- | --- | --- |
| 文本 | 结构化故事 JSON（8 幕 / 1098 字）+ 配音脚本（54 句） | 2 份 |
| 图像 | 角色设定图 1 + 场景插图 8 + 封面 1 | 10 张（另素材库 20 张） |
| 音频 | 4 音色有声书 + 程序化 BGM + 5 种音效 | 4 分 52 秒 |
| 视频 | 1080p 故事短片（画面 + 配音 + 硬字幕） | 4 分 53 秒 |
| 版式 | A4 绘本 PDF + 网页绘本 + 同步高亮网页 | 11 页 / 3 个页面 |

模态之间不是并列关系，是**同一条时间轴上的串联**：
文本的场景切分 → 决定配音的分段 → 决定字幕的时间码 → 决定视频每个镜头的时长。
改一句台词，四个模态一起变。这是本项目的技术主线。

### 1.3 选题来源

基于前八周作业（课程题目库第 2 项"多模态故事 Agent"与第 11 项"个人绘本生成器"的合并），
用同一个项目贯穿，每周叠加一个模态。

## 二、需求分析

### 2.1 目标用户

| 用户 | 场景 | 真实痛点 |
| --- | --- | --- |
| 6-8 岁孩子的家长 | 睡前讲故事，讲不动了 | 现成的故事书孩子听腻了，自己编又编不出来 |
| 幼儿园/低年级老师 | 班会、阅读课需要素材 | 做一套图文音视频齐全的素材要一整天 |
| 内容创作者（次要） | 批量产出儿童内容 | 角色一致性、配音、剪辑全靠手工 |

### 2.2 核心功能与优先级

| 优先级 | 功能 | 为什么这个优先级 |
| --- | --- | --- |
| P0 | 结构化故事生成（含分镜提示词） | 没有它，后面所有模态都没有输入 |
| P0 | 角色一致的多场景配图 | 这是"绘本"和"八张不相干的图"的分界线 |
| P0 | 多角色配音 + 时间轴 | 时间轴是音视频同步的唯一事实源 |
| P1 | 自动剪辑成片 | 决定"能不能发出去" |
| P1 | 绘本排版（PDF/网页） | 决定"能不能给孩子看" |
| P2 | 素材库检索 | 提升复用率，但不影响单次跑通 |
| P2 | Agent 编排 | 把七步压成一步，是体验优化不是能力新增 |

### 2.3 用户故事

**US-1（家长，睡前）**
> 作为一个讲不动故事的爸爸，我希望输入"我女儿叫小满，7 岁，喜欢数星星"，
> 就能拿到一本能直接念的绘本和一段能直接放的音频，这样我今晚不用再编了。

验收：输入到拿到 PDF + MP3 ≤ 5 分钟；绘本 8 幕；音频 ≥ 3 分钟；角色前后一致。

**US-2（老师，课堂）**
> 作为一个要上班会课的班主任，我希望同一个故事能有"看图（绘本）+ 听（音频）+ 看（视频）"三种形态，
> 这样我可以在不同环节切换，不用临时找素材。

验收：三种产物共享同一份故事；视频有字幕（照顾听障学生）；单文件可离线播放。

**US-3（我，作为开发者）**
> 作为一个要交作业的学生，我希望整条链路在没有 API Key 的电脑上也能跑通，
> 这样老师打开就能看到东西，而不是看到一堆 ImportError。

验收：`pip install -r requirements.txt` 后，四个 `run_weekX.py` 全部可执行。

### 2.4 非功能性需求

| 维度 | 要求 | 达成 |
| --- | --- | --- |
| 可复现 | 同一输入 → 同一输出 | 固定 seed + LLM 响应哈希缓存 + 全流程无随机数（除 BGM 旋律，已固定 seed） |
| 成本 | 单次全流程 ≤ ¥2 | 离线模式 ¥0；在线模式约 ¥1.4（8 张图 + 约 1.2 万 token） |
| 时延 | 全流程 ≤ 10 分钟 | 实测约 8 分钟（配音 75s + 视频 5min + 排版 10s） |
| 可离线 | 无网络也能看成品 | PDF / MP3 / MP4 / HTML 全部本地文件 |
| 可维护 | 换故事不改代码 | 换 `story.json` + `script.json` 即可 |

## 三、技术架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────┐
│  入口层  scripts/run_week{2,3,4,6}.py                     │
│          src/week0_web/index.html（浏览器）                │
├──────────────────────────────────────────────────────────┤
│  业务层  week1_story   结构化故事 + Prompt 策略            │
│          week2_illustration  配图 + 绘本排版               │
│          week3_tts     多角色配音 + 时间轴                 │
│          week4_video   Ken Burns 剪辑 + 字幕烧录           │
│          week5_rag     素材库 + 多模态检索                 │
│          week6_agent   工具编排 + 干预 + 留痕              │
├──────────────────────────────────────────────────────────┤
│  能力层  common/llm.py        重试 / 缓存 / JSON 修复 / 成本 │
│          common/schema.py     故事结构与校验               │
│          common/prompts.py    四种 Prompt 策略             │
│          common/audio_utils.py 编解码 / BGM / 音效合成      │
│          common/config.py     .env 加载与配置              │
├──────────────────────────────────────────────────────────┤
│  外部    DeepSeek/OpenAI · 通义万相/DALL·E · Edge TTS      │
│          FFmpeg · reportlab · sklearn · (可选) Chinese-CLIP │
└──────────────────────────────────────────────────────────┘
```

**分层的硬约束：业务层之间不互相 import。**
`week4_video` 不 import `week3_tts`，它只读 `timeline.json`。
这样任何一周的代码可以单独替换，也是第 7 周 Agent 能把它们当工具串起来的前提。

### 3.2 多模态数据流

```
创意 ──→ [检索] 模板/画风/音效建议
          │
          ▼
      story.json ──┬─→ [文生图] scene01..08.png ──┐
       (8 幕)      │                              ├─→ [排版] 绘本 PDF / 网页
                   │                              │
                   └─→ script.json ──→ [TTS] audiobook.mp3 + timeline.json
                        (54 句)              │
                                             ├─→ [剪辑] story.mp4（画面+字幕+配音）
                                             └─→ [网页] audiobook.html（高亮同步）
```

**唯一的"主干数据"是 `story.json` 和 `timeline.json`。**
其它所有产物都是它们的纯函数。这是整个设计里最重要的一条：
只要这两个文件是对的，任何一步失败了都可以单独重跑，不会污染上游。

### 3.3 技术栈

| 层 | 选型 | 版本 | 为什么不用别的 |
| --- | --- | --- | --- |
| 语言 | Python | 3.13 | 课程要求 |
| 文本模型 | DeepSeek / OpenAI 兼容 | — | 国内可直连，接口兼容 |
| 文生图 | 通义万相（主）/ DALL·E 3（备） | — | 国内直连 + 支持固定 seed |
| TTS | Edge TTS | 6.x | 免费、无需 Key、8 个中文音色、支持逐次调 prosody |
| 视频 | FFmpeg（imageio-ffmpeg 自带） | 7.1 | 不装系统 ffmpeg 也能跑 |
| 排版 | reportlab + PIL | 4.x | 精确控制 A4 版面；PIL 负责把标题烘焙进封面 |
| 检索 | sklearn TF-IDF / Chinese-CLIP | — | 见 4.4 |
| 前端 | 原生 HTML/CSS/JS | — | 单文件、零构建、双击即开 |

## 四、五个关键工程决策

### 4.1 角色一致性：特征卡 + 固定 seed + 参考图，而不是 LoRA

**问题**：8 个场景各自生成，女孩的脸会变。

**选项**：① 详细外貌 + seed；② 参考图条件生成（IP-Adapter 思路）；③ LoRA 微调。

**决策**：①+② 组合，放弃 ③。

**理由**：8 个场景的量级，LoRA 的训练成本和调参风险远大于收益；
而"把外貌写成不可变文本 + 用设定图锁像素"这两件事加起来，已经能到 8/8 一致。

**代价**：特征卡必须写得"可画"。
第一版写"活泼可爱"，生成出来每个场景都不一样；改成"左侧别一枚红色小发卡""抱一只掉了左耳的浅棕色兔子玩偶"之后才稳定。
**这是一次真实的返工，也是我对"prompt 要具体到能被画出来"最深的一次体会。**

### 4.2 视频：剪辑式而不是生成式

**问题**：要 5 分钟带字幕的故事视频。

**选项**：① 视频模型逐段生成（可灵/Runway）；② FFmpeg 把插图剪成视频。

**决策**：②。

**理由**：不只是钱（①约 ¥30-60，②¥0）。
更关键的是：**上一周刚把角色一致性做出来，用视频模型重新生成会把它毁掉。**
剪辑式还有一个隐性优势——完全可复现，改一个字幕重跑一遍，画面一帧不差。

**代价**：静态图容易"PPT 感"。用 Ken Burns（缓慢推拉 + 方向交替）解决，
推拉幅度定在 14%，超过 20% 就能明显看出"在放大"。

### 4.3 时间轴是唯一事实源

**问题**：字幕、配音、画面三者容易错位。

**决策**：TTS 阶段就把每句音频解码成 PCM，用 `wave` 读帧数算出毫秒级时长，
累加生成 `timeline.json`。视频剪辑和字幕烧录**只读这一份**。

**为什么不用 ffprobe**：`imageio-ffmpeg` 只带 ffmpeg 不带 ffprobe。
用 `wave` 读帧数反而更准（不依赖容器元数据），且零额外依赖。

**收益**：`timeline.json` 同时喂给了三个消费者（视频、字幕、高亮网页），
三者天然对齐，没有一处需要手工调偏移。

### 4.4 检索：双通道 + 可降级，而不是硬依赖 CLIP

**问题**：图像检索要用 CLIP，但 CLIP 要 torch（800MB）+ 模型（600MB）。

**决策**：`ClipEncoder`（装了就用）与 `TfidfEncoder + HSV`（默认）双实现，
接口一致，CLI 一致，产物一致。

**理由**：交作业的第一原则是"老师打开就能跑"。
让评审者先装 1.4GB 依赖，等于把验收门槛设在了自己这边。

**代价**：降级模式下图像检索本质是"用 caption 找图"，不是真跨模态。
实测 Q2（"怕黑的小女孩和灯笼"）R@5 只有 0.5，就是"怕黑"这种抽象语义抓不住。
这个数字我如实写进了评估表——**它正好说明了 CLIP 存在的意义**。

### 4.5 Agent：自研轻量循环 + 依赖图，而不是硬套框架

**问题**：要不要用 LangChain/LlamaIndex。

**决策**：自研 `StoryAgent`（约 260 行），工具层用统一 schema 描述，
`LLMPlanner` 与 `RulePlanner` 可切换。

**理由**：这个任务的编排是**确定的 DAG**（检索→写→画→配音→剪辑→排版），
不需要 ReAct 的"边想边试"。用框架反而要为了适配框架写一堆胶水，
而真正有价值的东西——**依赖图（改一个字段只重跑下游）**——框架并不会替你实现。

**代价**：没有现成的 callback / memory / 多 agent 能力。
但 `Tool` 的 schema 是标准结构，将来要迁到 LangChain 的 `StructuredTool` 只需改一层包装。

## 五、大模型工程方案

### 5.1 Prompt 管理

- 策略与代码分离：`src/common/prompts.py`，四种策略各有 `build_*()`，返回 `(system, user)`。
- 版本化：策略名即版本号（`schema_selfcheck` 是当前生产版本）。
- 对比实验：`data/raw_outputs/` 保留四份原始返回，`evaluate.py` 可复算全部指标。

**实验结论**（详见 `docs/作业1_Prompt策略对比.md`）：

| 策略 | 严格合规 | 平均字数 | vp 四要素齐全 | 加权总分 |
| --- | --- | --- | --- | --- |
| S1 零样本 | ✗ | 21.2 | 0/4 | 1.9 |
| S2 少样本 | ✓ | 40.0 | 0/4 | 6.9 |
| S3 角色扮演+CoT | ✗（5 幕 + 多字段） | 86.6 | 2/5 | 6.3 |
| S4 Schema+自检 | ✓ | **108.2** | **4/4** | **9.1** |

S3 文笔最好却不能用——**因为这条流水线的下一个读者是代码，不是人。**

### 5.2 调用设计：重试 / 缓存 / 降级

| 机制 | 实现 | 参数 |
| --- | --- | --- |
| 重试 | 指数退避 | 最多 3 次，等待 `min(2^n + 0.5n, 8)` 秒 |
| 缓存 | prompt 哈希 → 本地 json | 命中即返回，省 token 也保证调试稳定 |
| JSON 修复 | 三层候选 + 两层修复 | 围栏/配平切片/原文；去尾逗号 + 中文引号 |
| 二次追问 | 解析失败追加"只输出 JSON" | 最多 2 轮 |
| 降级 | `replay` / `manifest` | 无 Key 时读既有产物，接口不变 |
| 成本计量 | 按 token 估算 | 每次运行打印"调用 n 次 / 命中缓存 m 次 / ¥x.xxxx" |

### 5.3 成本控制

- **能缓存的绝不重算**：开发期反复调 prompt，缓存命中率约 70%。
- **能复用的绝不重做**：Agent 的依赖图让"改名字"只重跑配音/剪辑/排版，
  省下 8 张图的生成成本（约 ¥1.1）。
- **BGM 和音效程序化生成**：省掉素材采购与版权风险，体积为 0。

### 5.4 评估方法

三层，从便宜到贵：

1. **机器指标**（每次跑都算）：JSON 可解析率、Schema 通过率、场景数、平均字数、
   对白密度、visual_prompt 中文占比与要素齐全度。→ `evaluate.py`
2. **人工评分**（一次性）：结构可用性 / 文学质量 / 下游可生成性 / 成本，10 分制。
3. **端到端验收**（每次交付前）：抽帧看字幕、听音频、翻 PDF、点网页。

**为什么不全自动**：文笔好坏、角色像不像，机器判不了。
但"能不能被下游消费"必须机器判——这是 S3 那次踩坑教会我的。

### 5.5 用课程材料里的九维框架给自己的项目定位

课程阅读材料《后图灵测试评价体系》给了九个一级维度。拿它对照本项目，能说清"我评了什么、没评什么"：

| 维度 | 本项目是否覆盖 | 怎么体现 / 为什么没有 |
| --- | --- | --- |
| 认知能力（推理/规划/创造） | 部分 | Prompt 策略对比测的是"按约束创作"；Agent 的规划能力只到固定 DAG |
| 知识能力（事实性/幻觉） | 弱 | 儿童故事不依赖事实知识，这一维天然不适用；但 `schema` 校验相当于"结构幻觉"控制 |
| 行动能力（任务完成） | 强 | 六个工具端到端跑通、两个案例全绿、产物可直接使用 |
| 系统工程能力 | 强 | 重试/缓存/降级/成本计量/24 个单测/目录分层 |
| 人机关系（可干预性） | 强 | `intervene()` + 依赖图，改需求只重跑下游 |
| 伦理与价值 | 中 | 内容面向 6-8 岁，无暴力/恐怖；但没有做内容安全过滤（见改进方向） |
| 安全与可控 | 中 | 密钥不进仓库；但生成内容没有审核环节 |
| 可解释性 | 强 | 全链路 trace + 每个决策都在报告里写明理由 |
| 泛化能力 | 中 | 第二个案例证明"换故事不改代码"；但只在 2 个故事上验证过 |

**这张表的价值不是自夸，是把"没做到的"明确写出来。**
一门课的作业不可能覆盖九个维度，但至少要能说清自己在哪几维上站得住。

| 离线模式下"生成"是回放 | 换一个新创意需要 API Key | 这是刻意的设计取舍，不是缺陷；已在 README 明示 |

| 视频 108 MB 偏大 | 微信发送不便 | crf 26 可降到约 60MB，或出 720p 版本 |
| 只有一个故事经过完整人工润色 | 第二个案例的文本质感弱一些 | 用 S4 + S3 人设的组合策略重跑 |
| Agent 只支持"改名/改场景/改年龄/改主题"四类干预 | 创意类干预要 LLM 在线 | 加一个 instruction→request 的 LLM 解析器 |

## 九、反思

**技术上学到的三件事**

1. **接口比实现重要。** 这次 8 个 bug 里有 5 个是"两个模块各自都对，拼起来就错"——
   命名不一致、向量空间不一致、路径基准不一致。写代码前先把接口定死，比写得多快都值。
2. **"能跑通"和"能交付"是两回事。** PDF 从 48MB 压到 5.4MB、字幕从硬切改成按标点断行，
   这些都不影响"跑通"，但直接影响别人愿不愿意看。
3. **降级方案不是偷懒。** 没有 Key 就回放、没有 CLIP 就用 TF-IDF——
   把"什么条件下能跑"说清楚，比"假设一切就绪"专业得多。

**关于 AI 协作**

AI 把写代码的时间压到接近零，但它不知道我的约束（PDF 要能发微信）、
会自己发明验收标准（"能解析就算合规"）、写不出"为什么"（所有取舍理由都得我自己想）。

所以这次真正花时间的不是"写"，是**判断**：
选哪条路线、哪个指标才算数、哪个数字不能信。这部分 AI 帮不上忙，
也恰恰是这门课最想考的东西。
