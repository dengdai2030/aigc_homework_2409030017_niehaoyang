## 一、素材库里有什么

| 类型 | 数量 | 文件 | 字段 |
| --- | --- | --- | --- |
| 故事模板 | **10** | `templates.json` | id / 标题 / 世界 / 标签 / 适龄 / 一句话立意 / 五拍节拍 / 角色 / 画风 / 推荐音效 |
| 配图 | **20** | `images.json` + `images/` | id / 文件名 / caption / 世界 / 标签 / 来源 |
| 音效 | **5** | `sfx.json` + `sfx/` | id / 名称 / 描述 / 标签 / 时长 |
| 合计 | **35** | | 索引落在 `index/*.pkl` |

**20 张图怎么来的**：10 张来自主故事（角色设定图、封面、8 幕插图），
10 张是另外 8 个世界的参考图（太空 4、森林/海底/恐龙/雪山/糖果/沙漠 各 1），
全部为同一个项目内生成，风格统一（水彩 + 彩铅 + 米白纸纹）。

**5 种音效**：风铃、夜风、心跳、火柴划过、雨滴。
全部用 numpy 程序化合成（`src/common/audio_utils.py::make_sfx`），
版权干净、参数可复现、单文件 30-80KB。

## 二、检索架构：为什么做成"双通道 + 可降级"

```
                     ┌─ ClipEncoder（Chinese-CLIP）
   query ── 编码 ──→ │    文本塔与图像塔共享空间 → 图文分数可比
                     └─ TfidfEncoder（字符 1-3gram）+ HSV 分块直方图
                          降级方案：图片用 caption 文本进检索，
                          视觉向量只用于"以图搜图"
```

**为什么不做成硬依赖 CLIP**：Chinese-CLIP 需要 torch（约 800MB）+ 600MB 模型。
如果老师只是"双击看看能不能跑"，让他先装 1.4GB 是不现实的。
所以设计成：装了就用，没装就降级，**两种模式的接口、产物、CLI 完全一致**。

> 本机已装 `torch 2.15.0+cpu` 与 `transformers 5.21.0`，
> 但 Chinese-CLIP 权重（约 600MB）在本次环境里下载未完成，
> 所以下面的评估数字来自**降级方案**。
> 需要启用 CLIP 时设置 `HF_ENDPOINT=https://hf-mirror.com` 后直接跑同一条命令即可，代码不用改。

### 三个实现细节

**1. 字段加权靠"重复"，不靠改算法。**
TF-IDF 里标题、世界、标签各重复 3/3/2 次，等价于给这些字段加权。
不加权时查"太空冒险"，模板 `第 N 颗星` 排到第 5（被 4 张图挤下去）；
加权后升到第 3，Top1 稳定。这是最小改动、最大收益的一次调参。

**2. 两个向量，各管各的。**
- `vector`：检索用。CLIP 模式下图片用视觉向量（图文同空间）；降级模式下图片用 caption 文本向量。
- `vis_vector`：纯视觉，只用于 `similar_images()`（以图搜图）。

第一版把两者混在一个矩阵里，维度 4556 vs 112，直接崩。这个 bug 让我明白：
**"多模态"不是"把两种向量拼一起"，是"让它们在同一个空间里可比较"。**

**3. 索引缓存要连"向量化器"一起想。**
缓存只存了向量没存 sklearn 的 `TfidfVectorizer`，第二次启动就报
`NotFittedError: The TF-IDF vectorizer is not fitted`。
修法：命中缓存后重新 `fit_text()` 一次（35 条文本，毫秒级），比把整个 vectorizer 序列化更省事。

## 三、检索效果评估

5 个查询，人工标注相关素材（标注在 `evaluate.py` 的 `CASES` 里，可复核）：

| 查询 | P@5 | R@5 | Top1 返回 |
| --- | --- | --- | --- |
| 太空冒险 | 1.00 | 1.00 | 太空舱男孩抱火箭（IMG-11）✓ |
| 一个怕黑的小女孩和会发光的灯笼 | 0.60 | 0.50 | 绘本封面（IMG-02）✓ |
| 海底的珊瑚灯全灭了，鱼都不开心 | 0.40 | 1.00 | 灭掉的珊瑚灯（TPL-003）✓ |
| 雨夜街角那家只卖一分钟的商店 | 0.40 | 1.00 | 一分钟商店（TPL-010）✓ |
| 换牙的小恐龙躲在蕨类丛里 | 0.40 | 1.00 | 掉牙的小恐龙（TPL-005）✓ |
| **平均** | **0.56** | **0.90** | **Top1 命中率 1.00** |

**怎么读这张表**

- **Top1 全中**：说明"用户想找什么，第一个结果就是对的"——这是搜索体验里最重要的指标。
- **P@5 只有 0.56**：因为一个查询的相关素材本来就只有 1-5 个，分母固定是 5，
  命中 2 个就是 0.4。这个数字低不代表检索差，代表**标注集小**。
- **Q2 的 R@5 只有 0.5**：它同时涉及"夜晚 / 城市 / 灯笼 / 怕黑 / 分享"五个概念，
  字符 n-gram 抓不住"怕黑"这种抽象语义——它只能匹配字面。
  这正是 CLIP 该上场的地方：**图像塔不需要"怕黑"这个词出现在 caption 里，它看的是画面暗不暗、有没有一个光源。**

**已知局限（如实写）**
1. 降级模式下，图像检索本质是"用 caption 找图"，不是真正的跨模态；
2. 素材库只有 35 条，样本太小，P@5 波动大；
3. 没有做 query 改写（比如"太空冒险"扩写成"太空 宇航员 星球 火箭"），这是下一步最容易见效的改进。

## 四、结构化建议：从"检索"到"能拿去生成"

光返回一堆素材没用，得能直接喂给下游。`recommend()` 的输出长这样：

```json
{
  "input_idea": "海底的珊瑚灯灭了",
  "matched_template": {"id": "TPL-003", "title": "灭掉的珊瑚灯", "world": "海底", "age": "4-7"},
  "reference_images": [{"id": "IMG-16", "score": 0.41}, ...],
  "sfx": [{"name": "雨滴"}, {"name": "风铃"}],
  "next_step": {
    "story_request": {"protagonist": "（由孩子姓名替换）", "age": 7,
                      "scene": "海底", "theme": "灭掉的珊瑚灯",
                      "length": "中", "audience_age": "4-7"},
    "scene_plan": ["孩子戴上泳镜把头埋进水里", "水里有一扇贝壳做的门……", "..."],
    "style_prompt": "青蓝色水下光斑，气泡，柔和高光",
    "characters": ["主角（孩子）", "小丑鱼"]
  }
}
```

`next_step` 里的 `story_request` 就是第 2 周 `StoryRequest` 的入参格式——
**检索结果可以直接接进生成流水线**，不用人工翻译一遍。
这也是第 7 周 Agent 把 `search_materials` 放在第一步的原因：
先查库，再决定用哪个模板、什么画风、配什么音效。
